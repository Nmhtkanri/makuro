## 1. このマクロは何をするものか（1分サマリ）

**4つの経費ソース（jinjer / e-staffing / SAP Fieldglass / Freee）から月次の経費データを取り込み、
キーワード分類で社員別×カテゴリ別に集計し、jinjer給与インポート用CSVを出力する**バッチ処理。
（マクロにはカラー勤務表への書込機能もあるが、**現在は未使用のため移植対象外** →§6）

```
[入力] jinjer経費CSV / e-staffing / SAP経費CSV / Freee本社経費
   ↓ 貼り付け・整形・社員番号照合・重複削除
「経費統合一覧表」(34列・全ソース統合)
   ↓ 「設定」シートのキーワードで優先順位分類          ★移植の中核 (§4)
「集計」シート (社員別 A〜L列: 夜間当番/RINK/交通費/立替金/その他/テレワーク/顧客請求)
   ↓ 仕訳データ（通信手当等）をマージ ※人間確認用・移植不要（§6）
[出力] jinjer給与インポート用CSV   ※カラー勤務表書込は現在未使用・移植対象外
```

移植で価値が出る理由:
- 貼り付け→マクロ実行×5回前後の手作業を「月＋CSVアップロード→1クリック」にできる
- 分類ロジックがVBA＋設定シートに埋まっていて属人化している → Python＋設定ファイルで可視化・テスト可能に
- 勤怠チェッカー経費チェックモード（テレワーク日数・通勤費）と同じ画面に載せれば、
  テレワーク手当（申請金額）×テレワーク日数（打刻実績）の突合など相互チェックが将来可能になる

## 4. 分類・集計ロジック ★移植の中核（正確に再現すること）

### 4.1 入力レコード（経費統合一覧表 34列のうち分類が参照する列）

34列構造の由来 = **jinjer仕訳データCSV（33列）＋顧客請求分（34列目、e-staffing/SAP由来）**（§3の実データ参照）。
Python では34列全部を持つ必要はなく、以下の正規化レコードで足りる:

| フィールド | 元列# | 用途 |
|---|---|---|
| 社員番号 | 1 | 集計キー |
| 氏名 | 2 | 表示 |
| 合計 | 4 | 金額（主） |
| 金額(交通費) | 14 | 金額（合計=0のときの代用） |
| 備考(申請書データ) | 5 | judgeText用 |
| 交通機関 | 7 | 分類判定 |
| 内訳 | 8 | 分類判定（最重要） |
| 請求区分 | 10 | judgeText用 |
| 費用種別 | 11 | 分類判定 |
| 備考(明細) | 20 | judgeText用 |
| 計上日 | 21 | L列（請求日）＝社員ごとの最大値 |
| 仕訳区分 | 26 | 本社経費判定 |
| 顧客請求分 | 34 | G列判定・二重計上防止 |

### 4.2 判定テキストの定義（2種類あるのが最大の落とし穴）

```
judgeText  = 内訳 + 交通機関 + 請求区分 + 費用種別 + 備考(申請) + 備考(明細) + 仕訳区分   # 連結
nonTaxText = 内訳 + 交通機関 + 費用種別                                                    # 備考を含めない
```

**非課税精算(立替金)の照合は必ず `nonTaxText`（正式項目のみ）で行う。**
`judgeText` で照合すると「交通費（電車・バス）⇒通勤交通費（実費）に変更」のような**備考メモに残った旧分類名**を
非課税精算キーワードが先取りし、交通費(H)が立替金(I)に誤計上される（2026-06-30 修正済みのバグ。実測で89行・145,055円が誤分類していた）。
その他(kwEtc)は従来どおり `judgeText` 全体で照合する。

キーワード集合（kw〜）は「設定」シート（A=分類名, B=キーワード）由来。移植時は設定ファイル化する。

| 2 | 金額確定: 合計(4)を採用、0なら金額(交通費)(14)を代用 | — |
| 3 | 顧客請求分(34)が非空 かつ 内訳が夜間当番でない → **スキップ（二重計上防止）** | — |
| 4 | 仕訳区分(26)に「本社経費」 | **I** 非課税精算 |
| 5 | 内訳が kwYakan（夜間当番） | **D** 夜間当番手当 |
| 6 | 内訳が kwTW（テレワーク） | **K** テレワーク手当 |
| 7 | 内訳が kwRink（RINK） | **E** RINK手当 |
| 8 | `nonTaxText` が kwNontaxTatekae ※備考除外（§4.2） | **I** 非課税精算(立替金) |

## 5. SAP経費の前処理仕様（分類より前段。順序厳守）

`Paste_SAP経費_From_File`（CSV読込→`SAP_経費`シート書込の直前）で行う2つの補正。**8a→8bの順**。

### 8a. 夜間当番KWの業者名(D列)転記（Rev5〜）
- 判定: F列(説明)に夜間当番KWあり **かつ** D列(業者名)にKWなし
- 処理: **D列にF列の値を転記**（D列に既にKWがある通常行は変更しない）
- 理由: 下流の夜間当番判定（`IsNightDutyVendor`）は**D列だけ**を見るため、FのみだとG(顧客請求分)へ誤流出する

### 8b. 夜間当番手当の税抜化（÷1.1）
- 判定: D列 or F列に「**顧客対応**」または「**顧客当番**」の**部分一致**（「顧客対応当番16」「5/12 顧客当番16」等）
- 処理: C列(費用合計)を行ごとに `round(x / 1.1)`（四捨五入）で税抜補正。固定変換表ではなく**実額を割る動的処理**
- 背景: SAPは夜間当番手当を税込(10%)でエクスポートする。生の税込額 1,375 / 2,750 / 5,500 → 1,250 / 2,500 / 5,000（端数なし）

### ⚠️ 二重控除ガード（移植時は防御コードを入れること）
- **正しい入力＝SAPの生CSV（税込）のみ。** 既に税抜加工済みのデータ（1,250/2,500/5,000）を入れると二重控除（2,500→2,273）で誤る
- 生/加工の判別は**金額で行う**。クォートや日付の形式では判別できない —
  2026-06・2026-07 の実生CSV（07分は加工前であることを谷津さん確認済み）はどちらも**無クォート・`2026/5/17` 形式**なのに金額は税込2,750/5,500のままだった
  （AI解析ガイドの旧記述「生CSVはダブルクォート囲み」は実データに合わないため 2026-07-03 訂正済み）
- **Python実装では入力バリデーションを実装する**（VBAには防御がなく運用ルール頼み）。
  推奨: **夜間当番対象行の金額ベースで判定**する。税込額（1,375/2,750/5,500）が含まれていれば処理してよい。
  全対象行が税抜額（1,250/2,500/5,000）ちょうどなら「加工済みの疑い」でエラー停止

### SAP_経費 → 統合一覧表のマッピング（下流 `hSAP経費取り込みマクロ`）
- 姓+名／名+姓の両方向で jinjer 社員番号に紐付け
- D列(業者名)が夜間当番系 → 金額を合計(4)へ（=分類#5でD列・夜間当番手当になる）
- 非該当 → 金額を顧客請求分(34)へ（=分類#1でG列になる）

## 6. 出力仕様 — jinjerインポート用CSV（P2の移植対象・最終工程）

- 中間のR〜Y列振り分け（`dRY列振り分けマクロ`）・`I追加金額マクロ`（Q→X/Y）・`仕訳データ振り分けマクロ`（通信手当→R/S・T/U）は、

## 8. 検証方法（移植の合格ライン）

2026-06-30 のバグ修正時に実績のある**非破壊・全行突合方式**をそのまま使う:

1. 同一月の実データ（直近月の経費統合一覧表、約2,200行規模）を現行マクロとPython実装の両方に通す
2. **P1a**: 統合一覧表（34列）を現行マクロの「経費統合一覧表」シートと全行・全列で突合。
   **P1b**: 集計シート C〜L を全社員×全セルで突合し、**差分0** を合格とする（円単位）
3. 差分が出た行は分類トレースログで判定#とヒットKWを比較して原因を特定
4. 最低1〜2ヶ月は並行運用（マクロ本番＋Python検証）してから切替

注意: 現行マクロの主要Subは末尾に `MsgBox` があり headless実行（`Application.Run`）はハングする。
比較用のVBA側出力は手動実行 or 集計済みシートの値を使う。
